# 構成とファイルの役割

## リポジトリの構成

```
python-automations/
├── CLAUDE.md
├── README.md
├── docs/                      リポジトリ全体のルール（このフォルダ）。業務ごとの資料は置かない
├── pyproject.toml             sdk を import できるようにする設定と、sdk が使うライブラリ
├── requirements.txt           業務で使うライブラリ
├── sdk/                       2 つ以上の業務で使う部品
├── _template/                 新しい業務のコピー元
└── YYYYMMDD_業務名/           1 件 1 フォルダ
```

### Python の環境（`.venv`）

`.venv` はルートに 1 つだけ作り、全業務で使う。業務ごとには作らない。

- 自分の PC で実行する限り、業務どうしでライブラリの版がぶつかることはまずない
- 業務ごとに作ると、そのたびに環境を作る手間がかかり、同じライブラリが業務の数だけ入ってディスクの容量を食う

### `pyproject.toml` と `requirements.txt`

どちらもライブラリを書くファイルだが、役割が違う。

| | `pyproject.toml` | `requirements.txt` |
|---|---|---|
| 何のためか | `sdk/` を、どの業務フォルダからでも `from sdk... import ...` できるようにする | 業務のコードが使うライブラリを入れる |
| 書くライブラリ | `sdk/` の部品が使うもの（selenium・python-dotenv） | 業務のコードだけが使うもの（例：openpyxl） |
| 入れ方 | `pip install -e .` | `pip install -r requirements.txt` |
| 足す人 | `sdk/` を変える人（[sdkの決まり.md](sdkの決まり.md)） | 業務を書く人 |

- `pyproject.toml` が無いと、業務フォルダで `impl.py` を実行したときに `import sdk` が `ModuleNotFoundError` になる。`impl.py` を実行すると Python は業務フォルダの中だけを探し、1 つ上のルートにある `sdk/` を見つけられないため
- `pip install -e .` の `-e` は、`sdk/` をコピーせずにルートの `sdk/` を直接見に行かせる指定。`sdk/` を直したら、入れ直さずにすぐ全業務に効く
- 業務のライブラリを `pyproject.toml` に書かないのは、sdk の部品が使わないライブラリまで sdk の依存になり、どれが sdk に要るのかが分からなくなるため
- 業務で新しいライブラリが要るときは、ルートの `requirements.txt` に足す。`.venv` が 1 つなので、業務ごとのファイルには分けない

### 1 つの業務だけ版が合わないとき

ある業務だけ、ルートの `.venv` ではライブラリの版が合わないときは、その業務フォルダの中にだけ `.venv` と `requirements.txt` を作る。

- ルートの `requirements.txt` の版は変えない。変えると、ほかの業務が動かなくなる
- 業務フォルダの `requirements.txt` には、版を変えるライブラリだけを書く。ほかはルートの `requirements.txt` から入れる

```bash
cd 20261201_業務名
python3 -m venv .venv
.venv/bin/pip install -e ..                    # sdk
.venv/bin/pip install -r ../requirements.txt   # 全業務で使うライブラリ
.venv/bin/pip install -r requirements.txt      # この業務だけ版を変えるもの（後から入れたものが残る）
.venv/bin/python impl.py
```

その業務の `README.md` の実行方法には、ルートではなく業務フォルダの `.venv` を使うことと、上の作り方を書く。

## 業務フォルダ

```
YYYYMMDD_業務名/
├── README.md          何をするか・流れ・実行方法・出力
├── docs/              依頼文・依頼の背景・業務メモ
├── requirements.txt   この業務だけ版を変えるライブラリ（業務フォルダに .venv を作るときだけ）
├── .env.example       .env のキー名だけ
├── .env               値（git に入れない）
├── impl.py            入口
├── parameters.py
├── constants.py
├── schema.py
├── usecases/
├── components/
└── output/            出力（git に入れない）
```

### 名前の付け方

- フォルダ名は `YYYYMMDD_業務名`。日付は業務を始めた日。先頭に置くと一覧が始めた順に並ぶ
- 業務名は日本語でよい。業務フォルダは import されず、中で `impl.py` を実行するだけなので、Python の識別子にできない名前（数字始まり・日本語）でも動く
- 業務フォルダの中の `.py` とフォルダの名前は英語にする（[コードの書き方.md](コードの書き方.md#名前)）

### `.env` と `output/`

- `.env` は業務フォルダごとに置く。業務ごとにログイン先や認証情報が違うため
- `.env` と `output/` は git に入れない（[gitの使い方.md](gitの使い方.md#git-に入れないもの)）

### 業務の資料（`docs/`）

依頼文・依頼の背景・業務メモは、その業務フォルダの `docs/` に置く。ルートの `docs/` には置かない。

- 業務のコードと資料を同じフォルダに置くと、業務フォルダの名前を変える・消すときに、資料だけが残ったり名前が食い違ったりしない
- ルートの `docs/` はひな形から取り込むルールの置き場なので、各自の依頼文を混ぜると、ひな形のファイルと自分のファイルの区別がつかなくなる

| ファイル | 書くこと |
|---|---|
| `docs/依頼文.md` | 依頼のメール・チャットの原文。追加の依頼や質問への回答も、届いた順に足す |
| `docs/依頼の背景.md` | なぜ頼まれたか・今どうしているか（手作業の手順・かかっている時間）・期限 |
| `docs/業務メモ.md` | 相手の業務・システムの用語、決まり、例外。コードを書く・直すときに知っておくこと |

## 各ファイルの役割

| ファイル | 役割 |
|---|---|
| `impl.py` | 入口。`.env` を読む・ブラウザなど外とつなぐものを作る・usecase を順に呼ぶ。実処理は書かない |
| `parameters.py` | 実行時に受け取る引数（argparse）と、その型（dataclass） |
| `constants.py` | 固定の値。URL・画面の XPath・待ち時間・出力の列や文字コード |
| `schema.py` | 工程をまたいで受け渡すデータの型（dataclass） |
| `usecases/` | 業務の流れ。1 つの流れを 1 ファイルにする。画面やファイルの読み書きは components に任せる |
| `components/` | 画面の操作・ファイルの読み書き・データの変換。1 ファイル 1 役割 |

呼ぶ向きは `impl.py` → `usecases/` → `components/` の一方だけにする。components から usecases を呼ばない。
